# parity/: Latency Ladder reference ranker

This directory holds the reference ranking that every rung must reproduce, in two implementations that agree bit for bit:

- `ranker-ts/` is the TypeScript reference. It vendors cmdk 1.1.1's `command-score.ts` verbatim and adds `rank()`, the golden generator, the conformance runner and all test harnesses. It is npm workspace `@latency-ladder/ranker-ts`.
- `ranker-rs/` is the Rust crate `ladder-rank`, a port over UTF-16 code units. It builds for native and for `wasm32-unknown-unknown`, contains no `unsafe` code and has no runtime dependencies. It is a standalone crate and is not part of any root Cargo workspace.
- `ranker-rs/examples/wasm_probe.rs` is a scalar-only C ABI that lets Node drive the wasm32 build for `test:wasm`.
- `tables/` holds the frozen tables, generated in the pinned Chromium, plus the Node-vs-Chromium comparison.
- `goldens/` holds the hand-written edge goldens, shared by both implementations.
- `fixtures/` and `out/` hold generated fixtures and test outputs. Both are git-ignored and can be regenerated.

Background is in `docs/phase-0/05-software-foundations.md` §0 and §2.

## Normative rule (§2.2)

> `rank(items, q)`: if `q === ""` return all ids in dataset order. Otherwise, for each item compute `s = cmdkScore_1_1_1(item, q, [])` in IEEE-754 binary64, evaluated exactly as the vendored source with `Math.pow(0.999, n)` replaced by the frozen table `POW_0999[n]`. Return the ids with `s > 0`, ordered by `s` descending and then id ascending. Ties are exact binary64 equality. The selected item is `result[0]`, or none. Queries are used as typed: no trim, no normalization.

The rule has two conformance levels:

- **strict** requires an identical id sequence.
- **tie-insensitive** requires identical length, the same score at every rank and the same id set within each tie group. Only R1 may use this level.

"Evaluated exactly" means the way the pinned Chromium evaluates the code. That covers `String.prototype.toLowerCase` (full Unicode, root locale, with Final_Sigma), JS `\s`, UTF-16 `charAt` and `indexOf`, and `slice`. The Rust port encodes these semantics explicitly:

| JS semantics | How `ladder-rank` models it |
| --- | --- |
| strings are UTF-16 | `&[u16]` everywhere, and matching works unit by unit, so an emoji can match half a surrogate pair |
| `charAt(i)` out of range returns `""` | `Option<u16>` is `None`, and `None == None`, just as `"" === ""` |
| `slice(a, b)` clamps, and `b <= a` gives `""` | `count_in_slice` clamps both ends |
| `/\s/` | an explicit set: U+0009-000D, 0020, 00A0, 1680, 2000-200A, 2028, 2029, 202F, 205F, 3000, FEFF. This is checked against Chromium. Unlike `char::is_whitespace`, it excludes U+0085 and includes U+FEFF |
| gap regex `/[\\\/_+.#"@\[\(\{&]/` | an explicit set of 12 code units |
| `toLowerCase()` | a Chromium table plus a Final_Sigma rule (see below). `str::to_lowercase` is never used |
| `Math.pow(0.999, n)` | the `POW_0999` table |
| memo object keyed by `"si,ai"` | a dense `f64` table. The memoized function is pure, so the result is the same |

`ladder-rank` detects two cases that JS cannot score:

- **Upstream cmdk crashes on some queries.** The query must contain U+0130 İ and lowercase so that the transposition branch pushes `abbreviationIndex` past the end, for example `score("i̇", "İ̇")`. cmdk then recurses without bound and throws `RangeError: Maximum call stack size exceeded`. `ranker-ts` throws the same error. `ladder-rank` returns `Err(ScoreError::JsRangeError)`, detected at the exact state where JS starts recursing forever. Goldens record these queries as `{"qid","error":"RangeError"}`, and `conform` reports them as SKIP. The dataset already excludes U+0130, so this cannot occur there.
- **`POW_MAX = 4096`.** An item whose lowercased UTF-16 length exceeds 4096 units is rejected with `InputTooLongError` / `ScoreError::TooLong`. No real input comes close: an item of 80 code points lowercases to at most 320 units.

## Frozen tables (`tables/`)

All tables are generated by `ranker-ts/scripts/gen-tables.ts`. The script runs the same probe function in Chromium **141.0.7390.37** (Playwright build `chromium-1194`, `/opt/pw-browsers`) and in Node. Chromium's output is committed. The Chromium version and user agent are recorded in each file's `engine` field. Regenerating the tables is deterministic: a re-run reproduces identical bytes.

- `pow0999.json`: `bitsHex[n]` holds the binary64 bits of `Math.pow(0.999, n)` for n = 0..4096.
- `lowercase.json` contains:
  - `map`: every code point where `String.fromCodePoint(c).toLowerCase()` is not the identity, as UTF-16 units. There are 1,433 entries.
  - `sigma`: the Final_Sigma context classes, measured rather than taken from the UCD.
  - `jsWhitespace`: the units that `/\s/` matches.
  - `rules`: prose for the context rule.
- `engine-diff.json`: Node 22.22.2 (V8 12.4, ICU 78.2, Unicode 17) compared with Chromium 141.

**Final sigma rule.** U+03A3 Σ lowercases to ς when two conditions hold. First, scanning backwards over the original string by code point, skipping `preIgnorable`, the first code point exists and is `preCased`. Second, it is not the case that, scanning forwards and skipping `folIgnorable`, the first code point exists and is `folCased`. Otherwise Σ lowercases to σ. The classes were measured in Chromium with the probes `c+"Σ"`, `"A"+c+"Σ"`, `"AΣ"+c` and `"AΣ"+c+"A"`. ICU treats a code point that is both Cased and Case_Ignorable as ignorable, which is why the classes are measured. This is the only context-dependent mapping in the root locale. It is tested by fuzzing over the class members against Chromium.

**Node's V8 and Chromium differ:**

| | Node 22.22.2 compared with Chromium 141 |
| --- | --- |
| `Math.pow(0.999, n)`, n ≤ 4096 | **405 exponents differ**, each by 1 ULP (203 up, 202 down). The first are n = 16, 32, 103, 107 and 134 |
| effect on scores | unmodified cmdk run in Node differs from unmodified cmdk run in Chromium on **1,373 of 1.4M** fixture pairs |
| `toLowerCase` map | 55 code points differ, all assigned after Unicode 15.0 (U+10D50-10D65 Garay, U+16EA0-16EB8, U+1C89, U+A7CB-A7DC). Node lowercases them and Chromium does not |
| sigma classes | Chromium alone counts U+0295 as cased and U+1171E as ignorable. Node alone has 106 cased and 88 ignorable code points, all from Unicode 16 and 17 |
| `/\s/` | identical |

Rust's `f64::powf` on x86_64 Linux (glibc) matches Chromium 141's table on **all 4,097** exponents. On `wasm32-unknown-unknown`, `powf` differs from the table on **409** exponents. The spike's "V8 table" was Node's V8, which is exactly where Chromium 141 now differs. The table therefore remains mandatory: the pinned browser is the authority, and libm varies by platform.

Because `ranker-ts` must keep the vendored code verbatim, it uses the host engine's native `toLowerCase`. `rank-cli.ts` therefore checks the engine against the table at startup. If the data contains one of the disagreeing code points, it warns and exits with status 3. The dataset's Unicode ≤ 15.0 rule makes this moot under Node 22.

## Vendored source

`ranker-ts/src/vendor/command-score.ts` comes from cmdk `v1.1.1` (commit `fb4ea04e9ec211777fbb39c6104e3c5f2ee107d2`), file `cmdk/src/command-score.ts`. That file is unchanged on `main` at `dd2250e`, and its SHA-256 is `ccfd0d66…dfc7`. npm `cmdk@1.1.1` ships the minified form in `dist/chunk-NZJY6EH4.mjs`.

The file carries the MIT license header, a provenance note, an import and `// @ts-nocheck`. The only change to the code is `Math.pow(PENALTY_SKIPPED, x)` → `POW_0999[x]`, which occurs three times. `test/vendor-provenance.test.ts` reverses that substitution and checks the upstream SHA-256.

## Formats

- **Inputs.** Items are `{"schema":1,"items":["…",…]}`, and the id is the array index. Queries are `{"schema":1,"queries":[{"qid","q",…}]}`. The Rust CLI cannot read lone surrogates from JSON; the dataset bans them. The fuzz pipe sends UTF-16 unit arrays instead.
- **`rank-cli`.** Both CLIs support the same modes. `scores`, `ranked` and `golden` emit JSONL:
  - `scores`: `{"qid","scores":[bitsHex per item]}`
  - `ranked`: `{"qid","count","selected","ids","scores":[bitsHex]|null}`
  - `golden`: the golden line format below.
  - `bench` and, in Rust only, `fuzz-serve` are also available.

  A crashing query produces `{"qid","error":"RangeError"}`.
- **Golden line (§2.3).** Each line is `{"qid","count","idsSha256","selected","top":[[id,scoreBitsHex]×≤100],"tieGroups":[[scoreBitsHex,count],…]}`.
  - `idsSha256` is the lowercase hex SHA-256 of the UTF-8 string `ids.join(",")`.
  - `scoreBitsHex` is the 16 lowercase hex digits of the big-endian binary64 bits.
  - `tieGroups` lists every run of equal scores in rank order.
  - For `q === ""`, nothing is scored: the `top` scores are `null` and `tieGroups` is `[]`.
- **Conform.** `conform` reads a candidate JSONL of `{"qid","ids",["selected"]}`. A `ranked` file works as-is.
  - The output is `qid<TAB>PASS|FAIL|SKIP<TAB>code` plus a summary. It never includes query text or results.
  - `--verbose-local` adds `firstDivergentRank`, `expected` and `actual` ids. It is for humans only, never for held-out logs.
  - `tie-insensitive` needs `--items` and `--queries` whenever the hash differs, so that it can rebuild the reference tie groups.

## Commands

Run these from `parity/ranker-ts`. Node 22 runs `.ts` directly through type stripping.

```sh
npm install                       # at repo root (workspace); Chromium is preinstalled, never `playwright install`
npm run gen:tables                # regenerate tables/ in Chromium (+ Node comparison)
npm run gen:edge                  # goldens/edge-cases.src.json -> edge-cases.json (bits from hand derivations, not the scorer)
npm run fixtures                  # fixtures/f20k, f50k, f5k-clean
npm run verify                    # everything below
npm run typecheck && npm test     # tsc + node:test (edge goldens, provenance, conform)
npm run test:rs                   # cargo test (edge goldens, whitespace table, lowercase, slice/charAt)
npm run test:diff                 # TS <-> Rust rank-cli, scores/ranked/golden, bit-for-bit
npm run test:fuzz                 # 3 × 200k cases: Node oracle; Chromium oracle; Chromium oracle + wide Unicode
npm run test:wasm                 # wasm32 build run in Node vs ranker-ts on the 20k fixture
npm run test:bitexact             # vendored score vs UNMODIFIED cmdk dist in Chromium (+ edge goldens)
npm run test:oracle               # real cmdk React component in Chromium vs rank(), 100 queries × 5k items
npm run bench                     # ms/query at 50k items, Rust then TS
node scripts/golden.ts  --items I --queries Q --out goldens.jsonl
node scripts/conform.ts --golden G --candidate C --level strict|tie-insensitive [--items I --queries Q] [--verbose-local]
cd ../ranker-rs && cargo build --release && ./target/release/rank-cli golden --items I --queries Q
cargo build --release --lib --no-default-features --target wasm32-unknown-unknown
```

## Benchmark (50k-item fixture, 70 queries × 3 repeats, 4-vCPU Xeon @ 2.8 GHz, single thread)

| Implementation | mean | p50 | p95 | max |
| --- | --- | --- | --- | --- |
| `ladder-rank` (Rust, release, LTO) | **11.3 ms** | 8.5 ms | 29.9 ms | 43 ms |
| `ranker-ts` (Node 22) | **197 ms** | 131 ms | 556 ms | 664 ms |

Both times cover scoring and sorting only. Rust prepares (lowercases) the dataset once, in 24 ms; TS lowercases the dataset on every call, as cmdk does.

## Not done or caveats

- `npm install` for the workspace creates or updates the root `package-lock.json`. Nothing else outside `parity/` was touched.
- The fixtures are self-generated and deliberately include hazards: İ, Σ, NBSP, U+FEFF, U+0085, tabs, astral case pairs and one crash query. Once `dataset/` publishes `items.json` and `queries.json`, run `test:diff`, `golden` and `test:oracle` with `--items` and `--queries` pointing at them.
- The browser oracle checks only fresh-mount, single-`fill()` states. Typing-history order is out of scope (see §0.1).
- There is no JUnit output yet. `conform --report` writes JSON.
